# ADR-0003: 配对语义从「Dolev-Yao 可达性」改为「设计意图」

**状态**：已接受（2026-09-19）

## 背景

规范叙事视图（CONTEXT.md）表达协议**打算**怎么走：每条角色泳道内是设计上的消息流。MVP 的配对引擎（ticket 06）却用 Dolev-Yao 可达性做判据——只要接收模式无区分力、或候选非双向唯一，就不连线。结果是在四个内置样例上**全部零连线**：

- handshake-fixed / ns-original：接收步骤普遍是裸变量 `in(c, x: bitstring)`，被判「不可确定」；
- ns-mutual-auth：少数确定模式是「全变量元组」，形状互为通配，双向都不唯一。

US13「看到少数跨泳道连线」因此无法观察，用户认为配对功能根本没在跑。

## 决策

`pairSteps` 的语义改为**设计意图配对**：连线表达「设计上这条 `out` 发给这条 `in`」的 A→B 消息流，**不再**表达攻击者可达性。

判定规则：

1. 只连不同角色、同一信道的步骤。
2. **类型兼容**：用 `fun` 返回类型、角色参数、`in` 模式类型标注、`free` / `const` 类型做轻量类型推断；两侧类型都已知时须相等，缺类型按保守方向不匹配。类型不符直接淘汰。
3. **形状匹配**：构造子同名同元数、元组等长逐项递归；`in` 里的裸变量是通配符，但受类型约束。
4. **顺序配对**：仅当协议恰好两条泳道时启用——按「接收步骤在源码中的顺序」逐个选最早尚未使用的兼容 `out`，一对一消费。两方教科书协议的消息顺序即源码顺序。
5. 泳道多于两条时，自动配对关闭，全部标未配对：多方协议的消息路由无法从 `.pv` 静态推断（服务器中转、攻击者选择身份等），任何启发式都会画出错误的箭。

## 被否决的选项

- **保留 Dolev-Yao 唯一性**：真实样例恒零连线，功能不可观察（本 ADR 要解决的问题）。
- **纯顺序配对（不看类型）**：会把 `aenc(...)` 配给 `pkX: pkey` 之类的错位（ns-original 的预共享公钥输入），违背「画对优先于画全」。
- **对多方协议也跑顺序启发式**：实测 ns-mutual-auth 会产错误连线（responder 的 msg4 被配到 initiator 的攻击者输入），教学工具不能画错箭。
- **人工标注每份 `.pv` 的意图流**：正确但不自动，导入用户模型失效。

## 后果

- 「未配对」的含义随之改变：**无法可靠推断设计意图**，而不是「攻击者可能重放」。CONTEXT.md 词条同步更新。
- 配对**不是安全保证**：连上不代表消息在攻击者模型下达得到，验证结论只由 ProVerif 给出。
- 多方协议（含内置的 NS 互认证样例）在本版仍全部未配对；把「多方意图流」留作后续独立决策（可能需要消息编号注解或反例/执行序数据）。
- ticket 06 的验收（四样例零边）被本决策取代；其保守引擎相关测试按新语义重写。
- 需要解析器补 `fun` / `free` / `const` 签名（此前声明区整体跳过不建模）。
