# ADR-0003: 配对语义从 Dolev-Yao 可达性改为设计意图

**状态**：已接受（2026-09-19）

## 背景

规范叙事视图表达协议的设计意图：每条角色生命线内是设计上的消息流。MVP 的配对引擎（ticket 06）却以 Dolev-Yao 可达性为判据，只要接收模式无区分力、或候选非双向唯一，就不连线。四个内置样例因此全部零连线：

- handshake-fixed / ns-original：接收步骤普遍是裸变量 `in(c, x: bitstring)`，判为不可确定；
- ns-mutual-auth：少数确定模式是全变量元组，形状互为通配，双向都不唯一。

US13 要求看到少数跨生命线连线，该现象无法观察，用户因此认为配对功能没有运行。

## 决策

`pairSteps` 的语义改为设计意图配对：连线表达设计上这条 `out` 发给这条 `in` 的 A→B 消息流，不再表达攻击者可达性。

判定规则：

1. 只连不同角色、同一信道的步骤。
2. 类型兼容：依据 `fun` 返回类型、角色参数、`in` 模式类型标注、`free` / `const` 类型做轻量类型推断；两侧类型都已知时须相等，缺类型按保守方向判为不匹配。类型不符直接淘汰。
3. 形状匹配：构造子同名同元数，元组等长且逐项递归；`in` 中的裸变量是通配符，受类型约束。
4. 顺序配对：仅当协议恰好两条生命线时启用。按接收步骤在源码中的顺序，逐个选择最早且尚未使用的兼容 `out`，一对一消费。两方教科书协议的消息顺序即源码顺序。
5. 生命线多于两条时关闭自动配对，全部标未配对。多方协议的消息路由无法从 `.pv` 静态推断，服务器中转、攻击者选择身份等情形都会使启发式画出错误连线。

## 被否决的选项

- 保留 Dolev-Yao 唯一性：真实样例恒为零连线，功能不可观察，本 ADR 要解决的正是这一问题。
- 纯顺序配对，不看类型：会产生把 `aenc(...)` 配给 `pkX: pkey` 的错位，如 ns-original 的预共享公钥输入，违背画对优先于画全。
- 对多方协议也运行顺序启发式：实测 ns-mutual-auth 会产生错误连线，responder 的 msg4 被配到 initiator 的攻击者输入。教学工具不能画错连线。
- 人工标注每份 `.pv` 的意图流：正确但不自动，导入用户模型失效。

## 后果

- 未配对的含义随之改变：表示无法可靠推断设计意图，不表示攻击者可能重放。CONTEXT.md 词条同步更新。
- 配对不是安全保证：连上不代表消息在攻击者模型下可达，验证结论只由 ProVerif 给出。
- 多方协议（含内置的 NS 互认证样例）在本版仍全部未配对。多方意图流留作后续独立决策，可能需要消息编号注解或反例、执行序数据。
- ticket 06 的验收（四样例零边）被本决策取代；其保守引擎相关测试按新语义重写。
- 解析器需补充 `fun` / `free` / `const` 签名；此前声明区整体跳过，不建模。
