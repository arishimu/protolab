# 广播行的值层 / 事件对齐与「收到 ×N」梁堆叠

Type: prototype
Status: resolved

## Question

「人工配对：点选声明 / 广播扇出 / 接收端多行梁」定稿了广播行的形态（一行 = 一个 `out` + 它的全部 `in`，一条发送段 + N 条接收段，角标 `广播 ×N`），但把两件纵向编排的事交回了 map。要 prototype 定稿：

1. **广播行内多个接收端的本地内容贴什么 y**：一行有 N 个接收端时，各接收端的**值方块 / 算子簇 / event 菱形**是全部贴该行 y（共享行），还是各贴该角色本地位置（行只作信道段的锚点）？「人工配对」原型的定稿措辞是「仍贴各自角色列」，但没定行的 y。
2. **「收到 ×N」梁的堆叠上限 / 折叠**：接收端被多条消息收到时在多行各出现一次、用竖向梁连起；今天同角色多条梁按 13px 递进错开，端点一多就向外堆。

一并要回答的接口问题：

- 「广播 · 跨序」已是合法态（`docs/adr/0007`），**放宽了** `docs/adr/0006` 的「同 y 硬约束」；那么 ticket 08 的跨角色耦合规则（发送方单元边界 = 消息行 + 接收方簇底）在一行有 N 个接收端时如何推广？
- 「人工配对」原型的临时排布（局部序约束 + 配对合并行 → 拓扑排序 + y 空间最长路径）与 ticket 08 间距解算器的接口：行 y 由谁先出。

判据：`ns-mutual-auth` 的广播行（Message 2 & 5 合并成一行、`s_out2 → {i_in2, r_in5}`）在完整值层下仍然读得出「一条消息扇出到两处」，且不把「同一 y」误读成「同一个值 / 同一个时间点」。

## Answer

**HITL 定稿（用户确认「确定」）**：广播行 / 收到梁的问题被**信道唯一结点 + 一色一消息**模型取代。原型 `prototype/07-broadcast-row-alignment.html`（v3）为准。

### 1. 信道 = 扇出 / 合流的唯一结点

- **一发多收**：一条消息的发送端**唯一一条**进信道，信道把同一条消息**一分为多**，出到 N 个接收端。
- **多发一收**：N 条**不同消息**从各自发送端进信道，信道把它们**多合为一**，出到同一个接收端。
- 两者是**同一种画法**：「一根同色柱 + 抽头」，区别只在抽头落在哪一侧。

### 2. 各端 y 必须不同（取消「共享行 y」）

- 每个消息端直接落在**角色本地梯子 y**，不再有广播行共享 y。
- 直接结果：**「广播 · 跨序」不再存在**——R 的 `r_in5` 就待在 `r_out4` 之后（原型 740）。
- 因此**放弃** ADR-0007 点 2 的「同一 y」与 ticket 05「同一条消息 = 同 y」。

### 3. 一色一消息 + 信道管内同色柱

- **颜色 = 消息身份**（一条消息一种颜色）；与值层「一色一值」并列。
- **信道管加宽为多道**；每条消息一根**同色柱**，柱的跨度 = 该消息各端的 y 区间；柱道按 y 区间是否重叠贪心分配。
- 合流处进入同一步的抽头用**多色并排**表示多条消息。
- 1-1 消息也各一色、各有自己的柱（两端 y 不同则柱就跨这段，如 M6 900↔840）。

### 4. 整团 = 一个刚性间距单元

- 扇出 / 合流结构在纵向排布里是**一个计算单元**：内部端点的相对 y 固定（各由本地梯子给出），**整团移动**、不在团内插间隙、不参与等距压缩。
- 因此 ticket 08 的「跨角色耦合」在扇出 / 合流处**退化为整团刚性**：不存在「发送方单元边界 = 行 + 接收方簇底」这种跨角色等式。

### 5. 接口问题的结论

- **行 y 由谁先出**：问题**消解**——不再有共享行 y；各端 y 由各角色本地梯子给出，扇出 / 合流是一层刚性 overlay。
- **跨角色耦合推广**：**消解**，改为「整团刚性」。
- **「收到 ×N」梁**：**删除**，由合流的同色柱表达。

### 6. 资产与固化
