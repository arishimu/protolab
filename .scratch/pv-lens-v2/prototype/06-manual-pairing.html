人工配对：点选声明 / 一对多复用 / 复用梁的交互与视图状态

throwaway prototype · wayfinder ticket 09

问题：多方（命名角色 ≠ 2）默认「局部梯子」，未配对步骤给一个人工配对出口——把两条不同角色的消息端点声明为同一条消息。交互怎么做（含一对多）、视图状态长什么样？

判据：点选声明是否顺手（含一个源重复点选做一对多）；非法（跨信道 / 同向 / 同角色 / 重复声明）与警告（类型 / 形状）是否分得清；成环 / 与局部序矛盾是否显式标冲突；复用端点是否看得出「同一个步骤服务多条消息」；声明式意图边列表是否可见。

说明：纵坐标是临时算法（按发送端把配对归成广播行 + 接收端多行梁 → 拓扑 + 冲突消解 + 最长路径），不等于 ticket 08 的定稿间距模型；值层 / 本地步骤只留文本刻度（值层归 ticket 02/07）。角色按通联图分配在信道两侧：I 在左，R/S 在右；收发同侧时接收段下移 11px 错开。样例为真实 ns-mutual-auth.pv 的全部消息端。

素材
操作
提示点端点 → 点另一端点 = 声明；重复点源端点做一对多；Ctrl+Z 撤销

点选两端 · 一对多 = 一次广播

点一个端点选中，再点另一个不同角色 / 相反方向的端点即声明配对。同一个源可重复点选：先点 s1、s2，再点 s1、s3 ⇒ s1 把一条消息发送进信道，信道扇出到 s2 与 s3（一行、一条发送段 + 两条接收段，标「广播 ×N」）。非法点击当场给原因。

图例

信道总线（一等元素；同一信道只有一条）
未配对步骤：橙色半段，只到总线为止，不通到另一角色
人工配对消息行：紫色全程，标「人工」，与自动配对同 IR
冲突环：成环 / 与局部序矛盾，显式标记不静默重排
收到 ×N 梁：同一接收端被多条消息收到时，把它在各行的出现竖向连起（一对多发送不产生此梁）
广播：一条消息进入信道，信道扇出到多个接收方（一发送 + 多接收，同一行）
警告环：类型 / 形状不符，仅警告不阻断
跨线弧：走线跨过中间生命线时的绕行（ticket 01）
