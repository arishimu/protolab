# 规范叙事视图 v2：信息模型、视觉语法与交互

Status: ready-for-agent

## Problem Statement

pv-lens 当前的规范叙事视图把一个协议压成按角色排列的消息卡片。卡片能显示源码片段，却不能表达一条消息在信道中的完整路径、发送词项与实际到达词项的差异、值如何在每个角色本地绑定和派生，也不能可靠地表达多方协议的局部顺序。结果是读者会把不同角色的本地步骤误读成全局时间线，把同名词项误读成同一个实体，把信道误读成装饰，或者把不确定的路由误读成确定的连线。

`if`、`get`、`let`、`new`、`insert` 等本地操作还停留在消息卡片注释中。它们没有结构化的分支边界、绑定引用或构造/解构方向，因而无法支撑值层追踪、分支范围、密度折叠和自适应间距。`event` 也没有成为可查询的视觉对象，用户必须离开叙事视图手动理解对应性查询。

多方协议默认不自动配对是必要的保守边界，但 v1 没有给用户声明设计意图的出口。单纯把多方角色线性化、把广播画成多条相同连线，都会制造错误的时间和路由暗示。多信道还会让“信道色”“消息身份色”和“值身份色”互相争夺颜色语义。

## Solution

把 `.pv` 文本派生为一个明确的规范叙事 IR，再由确定性布局器产生可绘制的几何结果。纵轴表达每个角色自己的消息序梯子；消息、信道、值、事件和本地操作各自有稳定的视觉语法。信道是位于生命线之间的中性总线方块，也是扇出和合流的唯一结点；消息身份用消息色和值身份用值色，信道身份用几何而不占颜色。

视图分为消息层和值层。消息层保存跨角色的消息端点、发送方放上信道的 wire term、实际到达接收方的词项、信道和消息身份；值层保存每个角色本地的绑定、值方块、算子盒、事件标记和引用。两层只在接收端建立连接，不跨角色推断同一个实体。

布局器先用角色–信道消息步骤多重图求出生命线与信道的水平序列，再用单一弹性间距和硬约束解算纵向位置。多方保留局部梯子；自动配对仍只在可静态确定的两方协议启用。用户可以在画布上点选未配对端点声明意图，重复选择同一发送端形成广播；这些声明只保存在会话内存，并与自动配对使用同一个消息配对 IR。

事件旗标、对应性矩阵、密度折叠、源码联动、图例、缩放和滚动共同组成一个可读、可验证、可追溯的叙事视图。验证仍由 ProVerif 负责，叙事视图只表达设计意图和已缓存的对应性查询结果，不把可达性或攻击执行混入布局语义。

## User Stories

1. 作为学习密码学的学生，我想看到每个命名进程成为一条角色生命线，以便先建立协议的参与方结构。
2. 作为用户，我想在没有命名进程时看到内联 `process` 的 `main` 生命线，以便最小样例不会显示为空白。
3. 作为教师，我想看到角色参数簇固定在生命线顶部，以便解释每个角色可见的长期参数。
4. 作为协议研究者，我想看到 `!` 只标记角色或步骤可重复，而不复制出多条符号生命线，以便区分并发能力与会话实例数量。
5. 作为用户，我想看到 `|` 并行组合成为生命线或步骤的状态标记，以便知道源码中的并发结构仍被保留。
6. 作为读者，我想沿每条生命线从上到下阅读本角色的消息序梯子，以便不会把不同角色的本地顺序强行理解为全局时间线。
7. 作为读者，我想看到一条消息是一个跨角色对象，而不是两个互不相干的卡片，以便识别同一条设计意图的发送端和接收端。
8. 作为读者，我想看到发送段写发送方实际放上信道的 wire term，以便区分发送方表达式和接收方模式。
9. 作为读者，我想看到接收段写实际到达接收方的词项，以便知道 `in` 端的局部绑定或模式与 wire term 的关系。
10. 作为读者，我想看到箭头始终指向它抵达的目标，以便快速辨认发送段到总线、接收段到接收方块的方向。
11. 作为读者，我想看到跨越中间生命线的消息仍画成水平直线（不上拱、不绕行），以便不会把它误读成中继或额外的消息。
12. 作为读者，我想看到未配对步骤落在对应信道的挂轨上并带橙色开放圆点，以便明确工具没有臆造路由。
13. 作为安全协议研究者，我想让两方协议只有在信道、类型、形状和顺序都足够确定时自动配对，以便“画对”优先于“画全”。
14. 作为多方协议研究者，我想让自动配对在三方及以上协议中保持关闭，以便服务器转发或攻击者选择身份不会被错误连线。
15. 作为用户，我想点选一个未配对发送端再点选一个同信道接收端来声明设计意图，以便在多方协议中补充我知道的路由。
16. 作为用户，我想重复选择同一个发送端来连接多个接收端，以便把一次广播表达成一个扇出消息，而不是多条重复消息。
17. 作为用户，我想看到广播和合流都以信道为唯一结点呈现，以便一发多收和多发一收使用同一套视觉语法。
18. 作为用户，我想让广播端点保留各自的本地 y，而不是被强行放在同一行，以便广播不制造虚假的同时发生暗示。
19. 作为用户，我想让信道内的一条消息使用一根同色柱跨越它的端点范围，以便从颜色和柱形追踪消息身份。
20. 作为用户，我想在多条消息合流到一个接收端时看到多色并排抽头，以便分辨每条输入消息而不是看到一根含糊的线。
21. 作为用户，我想看到人工配对产生“人工”来源标记，并在会话刷新后清除，以便知道哪些关系来自我的当前声明。
22. 作为用户，我想在跨信道或端点方向不合法时得到明确警告且不建立配对，以便错误操作不会改变图的语义。
23. 作为读者，我想看到消息层与值层同时存在，以便区分“信道上流动的词项”和“角色本地持有的值”。
24. 作为读者，我想看到每个角色拥有自己的值绑定，即使两个角色写出同名变量，以便避免攻击场景下的跨角色等价误推断。
25. 作为读者，我想看到角色参数、`new`、`in`、`let` 和 `get` 产生稳定的绑定身份，以便沿本地引用追踪一个值的来源。
26. 作为读者，我想看到 `new` 名进入后续变量作用域，以便新鲜值能被后续方法盒和消息引用。
27. 作为读者，我想看到绑定值用值身份色方块显示，并在同一值被复制或等值检查时复用同色方块，以便理解“同色即同一值”的局部语义。
28. 作为读者，我想看到未绑定的内联构造使用虚线 wire 词项芯片，而不是生成新的值方块，以便区分新绑定和一次性构造结果。
29. 作为读者，我想看到 `adec`、`sdec` 等声明为析构的函数使用解构方法盒，以便理解它们从消息或输入值产生派生值。
30. 作为读者，我想看到 `encrypt`、`sign` 和元组等纯构造使用同一梯形族但朝消息方向横置，以便只用方向区分构造和解构。
31. 作为读者，我想看到方法盒输入、输出与复制的值方块紧贴盒体，以便不会因额外连线误读值的生命周期。
32. 作为读者，我想看到本地 `new`、`let`、`get`、`insert` 和普通 `if` 只占生命线上的本地节点，不占用消息箭头，以便消息路径保持清晰。
33. 作为读者，我想看到 `if` 与 `get` 的条件结构化为等值检查盒，以便明确显示比较的两个操作数和操作符。
34. 作为读者，我想看到 `&&` 与 `||` 的复合条件按子句分行并显示连接词，以便不用解析一整段源码文字。
35. 作为读者，我想看到无法结构化的条件保留 `unknown` 原文，以便信息不足时仍能阅读而不被伪造语义误导。
36. 作为读者，我想看到 `if` 的 `then` 与 `else` 使用并行臂道并在 `join` 合流，以便知道每个步骤属于哪条分支。
37. 作为读者，我想让 `then` 即使没有 `else` 也偏移到一条臂道，以便单臂分支仍然有可见范围。
38. 作为读者，我想让嵌套分支最多占两条主要臂道，更深层通过缩进和角标表示，以便复杂协议不会被无限增加的横向轨道撑爆。
39. 作为读者，我想看到空的 `else` 臂显示 `else ∅` 桩，以便区分“有空分支”和“没有 else”。
40. 作为用户，我想让 `branch…join` 整段作为刚性单元移动并默认展开，以便分支内部相对顺序稳定且守卫语义不会被默认隐藏。
41. 作为读者，我想看到 `let x = if c then a else b` 使用带 `?:` 的选择盒，而不是分支臂道，以便区分产出一个值的条件表达式和控制流分支。

## Implementation Decisions

- **真源和模块边界**：`.pv` 文本仍是唯一真源；规范叙事 IR、布局坐标和人工配对都是派生数据。实现继续保持 `core` 为无 DOM/Node 依赖的纯 TypeScript，`web` 负责 SVG 与交互，`server` 负责 ProVerif CLI。v2 的最高测试 seam 是 `source text -> narrative IR -> deterministic layout`，而不是组件内部状态或 SVG 像素。

- **core 解析模型**：`ParseResult` 输出角色、信道、函数与析构声明、查询、诊断、每角色有序 `items` 和顶层 `bindings`。每个角色 item 是消息端、本地步骤、事件标记或分支标记；`if` 不再作为普通本地步骤。消息端保留方向、信道 term、wire term、源码 span 和稳定端点 id。`new`、角色参数、`in`、`let`、`get` 各自产生稳定 binding id；`variable` 叶子带 `bindingId`，但不预计算反向引用。

- **条件和函数方向**：item 级守卫与 `PvTerm.conditional` 共用结构化 `Condition`，支持 `=`、`<>`、`&&`、`||` 和 `unknown` 原文兜底。`ParseResult.destructors` 来自 `reduc` 表头名；`ApplicationTerm` 不添加构造/解构布尔字段，渲染时查声明表。元组按结构性构造处理。

- **分支 IR**：一个条件展开为 `branch -> then items -> else? -> else items -> join` 的连续标记流。`branch` 携带 guard、`else` 与 `join` 通过稳定 id 关联；不存臂范围，布局器扫描标记流取得范围。引用解析使用 branch/else/join 的 arm frame stack，从内向外取最近绑定。

- **消息配对 IR**：core 纯函数将自动配对和人工意图合成统一的 `MessagePairing`，字段至少包含 `outEnd`、`inEnd` 和 `origin`（自动或人工）。未配对端保持 `MessageRow` 的独立分支，不用 `in: null` 伪造半条消息。人工声明只存会话内存，不回写 `.pv`，也不产生像素坐标。

- **自动配对边界**：自动配对只对恰好两条角色生命线启用；候选必须同信道、类型兼容、结构形状兼容，并按接收源码顺序消费最早的未使用发送端。多方自动配对返回空集。跨角色同名变量、同名值或局部绑定不自动等价。

- **人工配对交互**：画布点选未配对 `out` 后再点选同信道未配对 `in` 建立声明；允许一个发送端重复点选多个接收端形成广播，不支持拖拽、局部序号输入或直接移动自动配对。跨信道、方向错误和已自动配对端拒绝操作；类型不符可以建立带警告的设计意图，但不得静默改变自动配对。成环或不可满足的行序约束在布局结果中显式标冲突。

- **广播与合流**：信道是扇出/合流唯一结点。一发多收是一条入信道段和多条出信道段，多发一收是多条入信道段和一条出信道段；两者共享同色消息柱和抽头语法。各端使用角色本地 y，不共享同一 y，不绘制“收到 ×N”竖梁，也不使用“广播·跨序”作为错误状态。扇出/合流整团是一个刚性计算单元，团内不插间隙、不参与弹性压缩。

- **水平序列**：水平轴是角色与信道的交错排列。输入图的每个消息步骤产生一条角色–信道边，重复步骤计为边权，不依赖自动或人工配对。求解目标为 `argmin_sigma max_k cut(k)`；同目标取降序 cut 曲线字典序最小者，再按角色 `narrativeRoleOrder` 和信道首次出现源码序取字典序最小者。退化情况由同一套规则处理，不另设特例。求解器提供外部顺序约束 seam，但 MVP 不提供手动排列控件。

- **纵向间距**：画布高度由内容决定。使用唯一连续紧凑度参数驱动 `gap.unit`，范围为 `[18, 26]`；`gap.row`、`gap.group` 和 `gap.tight` 从它派生并各自有绝对下限。等距是初值，硬约束通过局部插值优先满足；压缩按 group、row、tight 的下限自然触底。计算单元是参数簇、值方块、算子簇、事件、本地步骤、折叠条、分支团和消息团。参数簇与算子簇内部永不压缩；消息端 y 全局唯一，复用、人工配对、扇出/合流和不重叠约束不可被等距覆盖。约束成环或顶死时标冲突并延长生命线。

- **消息层视觉**：角色为竖直生命线，信道为生命线之间的高而扁的中性竖直总线方块。消息段把发送词项或实际到达词项写在箭杆中间的消息块内；箭头指向总线或接收方块。配对消息使用消息身份色，未配对端使用橙色开放圆点；跨越中间生命线或信道的连线一律画水平直线（见 ADR-0010）。信道不使用颜色。

- **颜色和可访问性**：消息身份色固定为八个循环 token：`#2563EB`（蓝）、`#0891B2`（青）、`#16A34A`（绿）、`#D97706`（琥珀）、`#DC2626`（红）、`#7C3AED`（紫）、`#DB2777`（粉）、`#475569`（石板）。值身份色固定为八个浅色填充 token：`#BFDBFE`、`#A5F3FC`、`#BBF7D0`、`#FED7AA`、`#FECACA`、`#DDD6FE`、`#FBCFE8`、`#CBD5E1`，值块统一使用 `#1F2937` 深色边框和文字。消息色只用于消息柱、消息段和箭头，值色只用于值方块；两组不在同一图形载体上混用。未配对点固定为 `#C2410C` 的橙色开放圆点，冲突标记使用 `#B91C1C` 加三角/斜线图形。每个消息和信道同时有稳定序号字形，消息柱使用实线/短虚线/点线循环线型，值块保留文字或绑定短名，因此灰度、色觉缺陷和打印场景仍可区分。文本使用系统无衬线字体，源码和 wire term 使用等宽字体，不使用负字距或只靠颜色表达状态。具体 token 由所有组件和图例复用，消息序号超过八个时按序号和线型继续区分而不新增临时颜色。

- **值层视觉**：值方块镶在对应生命线，按值身份一色一值。解构和构造共用倒置等腰梯形方法盒，短底与值方块宽度一致；解构从信道向生命线竖向布置，构造从生命线朝消息横向布置。输入、等值输出和同一绑定的再次引用复制同色方块；新绑定产生新色；未绑定内联构造显示虚线 wire 词项芯片。移除独立派生边和“用于发出”连线，依靠同色垂直编排、绑定引用和信道内 wire term 追踪。

- **分支视觉**：守卫在主生命线上显示无输出的等值检查盒，两个操作数以同色值方块贴在盒上方。内嵌解构先显示解构盒，其派生虚线芯片喂给检查盒。复合条件逐子句成行，连接词以字形显示。then 和 else 是并行臂道，then 恒偏移一条道；臂道号为外层 else 深度加一，主要轨道封顶两条，深层使用缩进和角标。空 else 画 `else ∅` 桩。`branch…join` 是刚性单元，默认展开，只提供显式折叠开关。条件表达式使用 `?:` 选择盒并在盒外显示条件芯片，不生成分支臂道。

- **事件和批量对应性**：事件标记叠加在值/消息节点上，前提端为填充菱形，结论端为实心圆点加斜旗。进入事件交互时，系统按同一参数集合预生成全部有序对 `inj-event(e_i) ==> inj-event(e_j)`，把生成 query 插入待验证文本的 `process` 之前并缓存结果。矩阵可开合且每格可点击；点击矩阵格或旗标双向选中，行列中的每格保留自己的判定色，当前项增加环和加粗。详情展示生成的 query 原文，并复用现有 trace 入口。

- **密度和折叠**：算子簇默认采用分段折叠骨架，折叠块直接显示内含算子名和数量；下方保留后续仍引用的虚线幽灵值块，悬停显示细节浮卡。角色整体折叠只隐藏细节、不改变行距。分支团默认展开，不能因为普通密度设置自动折叠。

- **源码、图例和视口**：源码面板只读，图中任一带 span 的对象都可反向高亮源码，源码行也可高亮图中对象。图例解释颜色、线型、形状、开放圆点、消息柱、值方块、方法盒和事件旗，并显示当前图中实际使用的消息/值序号。画布提供 `−`、`100%`、`+` 和“适合宽度”四个缩放控件，缩放范围为 60%–180%，步长 10%；鼠标滚轮只滚动容器，缩放通过控件或键盘快捷键触发。水平和垂直滚动由外层容器承担；不通过缩小字体解决内容高度，布局超出视口时保留完整几何。

- **诊断和验证集成**：解析 `degraded` 保留为原文标注段，`error` 显示带行列的错误诊断；诊断可以归入角色或未归属区。叙事视图不改变现有查询结果、反例 trace、完整 stdout、ProVerif CLI 超时和取消语义。`cannot be proved` 始终显示为“未证出”。

- **原型依据和 ADR 关系**：信道拓扑、值层、事件、密度、多方局部梯子、core 模型、间距、人工配对、广播合流、水平序列、分支画法和多信道视觉分别沿用已验证的 v2 原型与 ADR-0004 至 ADR-0010。ADR-0008 已取代早期广播方案的共享 y 和“收到 ×N”梁；ADR-0009 已取代角色左右二分和同侧 jog；实现不得恢复这些旧规则。

## Testing Decisions

- 好测试只断言外部行为：给定 `.pv` 文本、人工意图和验证记录，产生的 IR、配对来源、布局约束、几何关系和用户可见状态必须稳定；不测试 React 内部状态、CSS 具体像素或实现私有函数的调用次数。

- **最高 seam：叙事 IR 到确定性布局**。给定 `ParseResult`、自动/人工 `MessagePairing` 和外部顺序约束，断言水平序列、局部梯子、消息团/分支团刚性、全局 y 唯一、冲突诊断、折叠幽灵块和内容驱动高度。相同输入重复运行、打乱候选枚举顺序都必须得到相同结果。

- **core 模型 seam**：使用四个既有基准样例、三信道样例和最小合成文本，断言角色/信道顺序、item 标记流、branch/else/join 连续区间、Condition 结构、destructors、binding id、分支 arm frame 引用解析、`PvTerm.conditional` 和降级诊断。不得把跨角色同名变量合并。

- **配对 seam**：覆盖两方同信道类型/形状/顺序配对、不同信道拒绝、类型不符保守不连、多方自动空集、人工一对一、一对多广播、多发一收、来源字段和会话内存清除。断言广播/合流不共享 y，且信道柱的消息身份保持一致。

- **布局算法 seam**：为 min-max、tie-break、孤立角色、空边集、单信道、多信道、跨信道角色和 `processK` 等 fixture 断言序列与 cut 曲线；回归原型已验证的 `ns-mutual-auth` 序列 `S · I · c · R · K` 和 min-max/min-sum 见证数字。测试外部顺序约束作为输入，不测试未来拖拽 UI。

- **视觉语法 seam**：React/SVG 只做冒烟和语义查询，断言四个基准样例可以渲染、出现角色/信道/消息方向/值方块/事件/图例/未配对诊断、没有配对时没有跨角色连线，人工广播和多信道产生正确的 aria-label 或 data identity。保持现有 render-to-string 先例，不做像素黄金图。

- **事件查询 seam**：使用录制的 ProVerif stdout 和批量 query 生成器，断言 query 插入 `process` 之前、全部有序对数量正确、缓存命中、`true`/`false`/`cannot be proved` 映射正确、矩阵和旗标选择双向联动，反例 trace 原文仍可进入现有结果面板。

- **源码联动和诊断 seam**：断言任意可见节点的 source span 能定位到正确行列，源码反向选择不会选中同名但不同 binding 的节点，角色内诊断与未归属诊断各出现一次，未知语法不会抛异常。

- **先例**：继续使用仓库已有的 Vitest fixture 测试、core parser/pairing 黄金断言、web narrative layout 纯函数测试、render-to-string 冒烟测试和 server ProVerif 集成冒烟。验证 CLI、超时和真实 ProVerif 运行保持现有非 CI 必跑的集成边界。

## Out of Scope

- 反例/执行（攻击）视图、ProVerif derivation、攻击者路径的几何归因和多会话实例展开。
- ProVerif `-graph` / `-html` 攻击图导出以及由攻击图反向生成叙事关系。
- 画布编辑、拖拽生命线、拖拽端点、保存人工配对到 `.pv` 或从图回写源码。
- MVP 中让用户手动覆盖水平序列；只保留接收外部顺序约束的 seam。
- 把信道、角色或值的跨角色同一性推断为可达性事实；规范叙事视图不替代 ProVerif 结论。
- 支持完整 ProVerif 语法、观察等价、choice 等高级语义；无法可靠结构化的语法继续降级为原文诊断。
- 用自动布局引擎、像素快照或字体测量锁定具体渲染实现；布局合同只约束可观察的几何关系和语义。
- 多用户、云端保存、账号、公共部署、ProVerif 打包分发和验证性能优化。

## Further Notes

- 这份规格接收了 v2 effort 的全部已验证取舍。原型已覆盖单/多信道、值层、事件矩阵、密度折叠、人工配对、广播/合流、条件分支、水平序列和多信道视觉；`ns-mutual-auth`、`ns-original`、`handshake-fixed`、`hello` 以及三信道合成 fixture 是实现和回归的最小素材集。
- 视觉细节中唯一由本规格补齐的部分是颜色、字形、图例和视口规则：颜色只编码消息和值，信道用几何；颜色始终有序号、线型或形状作为辅助通道。具体 CSS token 可以在实现阶段集中调整，只要保持上述语义和可访问性约束。
- 批量对应性查询的成本已用四个内置样例实测可接受；查询必须插入 `process` 之前。生成器、缓存和验证结果属于叙事视图的辅助能力，原始 `.pv` 文本仍不可变。
- 多信道 fixture 当前解析和配对不会崩溃；主进程只有 `new` 而没有消息时，尾部无法挂载的标注仍按既有 degraded 诊断跳过。该行为属于现有 parser 边界，本规格不把它扩大为新的语义承诺。
- “每侧最忙角色靠近信道”是水平序列 tie-break 的自然后果，不得作为另一条显式启发式加入实现。任何未来水平编辑都应通过外部约束重新求解，而不是写入固定像素或破坏 min-max 目标。
